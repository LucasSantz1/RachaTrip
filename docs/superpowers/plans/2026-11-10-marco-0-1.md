# RachaTrip — Marco 0 e Marco 1: plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fundação do repositório (backend, frontend, Docker, CI) e núcleo financeiro testado: validação de centavos, divisão, saldos, acertos e models com constraints.

**Architecture:** `backend/trips/ledger.py` concentra as regras de dinheiro em funções puras sem Django, testadas primeiro e localmente. Depois vem o Django + DRF + MySQL em Docker, os models com constraints no banco, o esqueleto Next.js servido no mesmo domínio via rewrites e o CI.

**Tech Stack:** Python 3.13 (container) · Django 5.2 LTS · DRF · mysqlclient · MySQL 8.4 · pytest + pytest-django · ruff · Next.js (App Router) + TypeScript strict + Tailwind + shadcn/ui · Node 24 · Docker Compose · GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-10-rachatrip-design.md`

## Global Constraints

- Dinheiro é sempre `int` em centavos. Nenhum `float`, `Decimal` ou `str` representa valor monetário em código de produção.
- `ledger.py` não importa nada do Django.
- Limite de valor: `1 ≤ amount_cents ≤ 100_000_000`.
- Tokens: o banco guarda só SHA-256 em hex (64 caracteres). Token puro nunca é gravado.
- Segredos só via variáveis de ambiente, lidas com `os.environ` (sem django-environ). `.env` nunca é commitado.
- Nenhuma dependência fora da tabela de stack da spec. Versões: a última versão estável de cada pacote no momento da tarefa, fixada com `==` nos arquivos de requirements e no `package-lock.json`.
- Textos visíveis ao usuário em português do Brasil.
- Todo commit termina com a linha `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Atalho deliberado ganha comentário `shortcut: <limite>, <quando evoluir>`.

## Pré-requisito do ambiente

Docker não está instalado nesta máquina. As Tasks 1–6 rodam com o Python local (3.15) num venv. **A partir da Task 7 é necessário Docker Desktop instalado.** Se não estiver, a execução para antes da Task 7 e avisa.

## Review Focus

1. `True`/`False` como valor: `bool` é subclasse de `int` em Python; `validate_amount_cents(True)` tem que falhar com `amount_not_integer` (teste na Task 3).
2. Parte de 0 centavo: 1 centavo dividido entre 3 gera partes `1, 0, 0`; quem ficou com 0 aparece no resultado e não gera transferência (testes nas Tasks 4 e 6).
3. Pagador que é o único da divisão: saldo líquido 0 e nenhuma transferência (teste na Task 6).
4. Viagem sem despesas: saldos todos 0 e lista de transferências vazia, sem erro (teste na Task 5).
5. Nomes com acento e emoji (`"Zé 🚗"`) gravam e voltam iguais no MySQL; `"Ana"` e `"ana"` na mesma viagem colidem pela collation `utf8mb4_0900_ai_ci` (testes na Task 8).

**Files:**

**Interfaces:**

    - `sum(b.paid) == sum(b.consumed) == soma dos valores`;
    - `net == paid - consumed` para cada participante.

### Task 6: `suggest_settlements` (M1-4)

**Files:**
- Modify: `backend/trips/ledger.py`, `backend/trips/tests/test_ledger.py`

**Interfaces:**
- Consumes: `Balance`, `compute_balances`.
- Produces:
  - `class Transfer(NamedTuple): from_id: int; to_id: int; amount_cents: int`
  - `suggest_settlements(balances: Mapping[int, Balance]) -> list[Transfer]`. A ordem das chaves de `balances` é a ordem de cadastro, usada para desempate.

- [ ] **Step 1: Testes que falham**
  - Todos quites → `[]`.
  - `{1: net 3000, 2: net -1000, 3: net -2000}` → `[Transfer(3, 1, 2000), Transfer(2, 1, 1000)]`.
  - Desempate: `{1: +500, 2: +500, 3: -1000}` → `[Transfer(3, 1, 500), Transfer(3, 2, 500)]`.
  - Pagador único da divisão (via `compute_balances` com `1` pagando 1000 e `shares={1: 1000}`) → `[]` (Review Focus 3).
  - Participante com parte 0 (1 centavo entre 3, pago por `1`) → nenhuma transferência envolvendo quem ficou com 0 (Review Focus 2).
  - Soma de `net` ≠ 0 na entrada → `LedgerError` com `code == "balances_not_zero_sum"`.
  - Aleatório (1000 casos, saldos gerados via `compute_balances`). Garantias:
    - aplicar as transferências zera todos os saldos;
    - `len(result) <= n - 1`;
    - todo `amount_cents > 0`;
    - `from_id != to_id`;
    - duas chamadas iguais dão o mesmo resultado.
- [ ] **Step 2:** rodar → falha.
- [ ] **Step 3:** implementar o guloso:

```
pos = posição de cada id em balances
restante = {id: b.net}
enquanto houver restante > 0:
    credor  = id com maior restante > 0      (empate: menor pos)
    devedor = id com menor restante < 0      (empate: menor pos)
    valor = min(restante[credor], -restante[devedor])
    adiciona Transfer(devedor, credor, valor); atualiza os dois restantes
```

  A cada passo pelo menos um saldo zera, por isso são no máximo `n − 1` transferências. Com até 50 participantes (limite da spec), buscar o máximo com `max()` a cada passo é suficiente.
- [ ] **Step 4:** rodar → passa. `ruff check .` limpo.
- [ ] **Step 5: Commit** `feat(ledger): sugestão de acertos`.
